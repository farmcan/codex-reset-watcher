# Missed Astra reset announcement

The hourly official poll was healthy at 2026-09-08 02:00 UTC. D1 already
contained Tibo's [September 7 announcement](https://x.com/thsottiaux/status/2097043464538264003),
published at 19:24:57 UTC, but no corresponding signal existed.

The classifier required a recognized product/context phrase and a relative
future-time keyword. The announcement used Astra, “global reset of the usage,”
and a clock time instead. It was therefore discarded as unrelated after ingestion.

The repair recognizes Astra context, the global-usage-reset phrase, future reset
intent, and explicit PST/PDT/UTC landing times. The dashboard labels a scheduled
hard reset whose effective time has passed as awaiting completion confirmation,
without recommending front-loading usage. An announcement never automatically
becomes a completed reset merely because its scheduled time has passed.

The missed post is backfilled as `scheduled_reset`, `hard_reset`, `first_party`,
A1, with an approximate effective time of 2026-09-08 02:00 UTC. This follows the
literal PST abbreviation in the post; colloquial Pacific daylight time would be
one hour earlier. The user reported receiving a reset, but that report is not
stored as a global first-party completion confirmation. The confirmed-reset
clock and audited history therefore still require completion evidence.

The backfill uses the stored post and repaired classifier, inserts only the
missing signal, and suppresses historical email delivery. Regression coverage
includes the announcement, clock-only landing language, and unrelated/negated
Astra content. `npm run check` passes (30 tests, typecheck, historical audit,
and deployment dry run); expired-notice UI behavior was also checked directly.

## Automatic review failure, resolved later September 8

The initial Qwen integration had only been verified from Node, plus ten manually
written review results. Every scheduled Worker review failed before contacting
the provider: the deployed runtime rejects `redirect: 'error'`. The generic catch
message concealed that runtime error. This was not an observed Qwen 429 rate limit.

A protected one-post review endpoint reproduced the exact failure on the deployed
Worker. The fix uses `redirect: 'manual'` and rejects non-success HTTP responses,
so credentials are not forwarded to redirect destinations. The same deployed
endpoint then successfully called Qwen and persisted the result (the Tibo-only
completion count increased from one to two at 2026-09-08 13:22 UTC).

At the user's request, model review now covers only `@thsottiaux`; other sources
use rules. Pending/retrying non-Tibo reviews are excluded without deleting posts
or completed reviews. Each request reviews one post, with two concurrent requests
and at most twenty posts per run. Error diagnostics distinguish model failures
from persistence failures and redact credentials. UI counters separately show
queued posts and failed posts awaiting retry, scoped to Tibo only.

Recovery verification: the deployed Worker completed all 31 stored Tibo posts by
2026-09-08 13:25:10 UTC, with zero pending reviews, zero retries, and no last error.
The protected endpoint rejects unauthenticated requests with HTTP 401. All 42 tests,
type checking, the historical audit, and the deployment dry run passed.
